A step-by-step walkthrough for cutting a production release of the Food Related app — flipping the environment config, swapping Google service files, bumping version numbers, and pushing the build through Xcode and the Play Console.

Platforms: iOS & Android Stack: React Native Env flip: devFR → prodFR Editor: VS Code
01

Open the project

Pick a code editor and get oriented in the app folder

Open the project in the code editor you're most comfortable in — this runbook uses VS Code. Inside the app folder, navigate to Utils/utils.js, which is where the environment switch for the release lives.

For reference, this is the shape of the app folder you'll be working in:

app ├─ API │ ├─ analyticsErrorLogger.js │ ├─ errorHandler.js │ ├─ networkAPI.js │ └─ paths.js ├─ Analytics ├─ AppRoutes │ ├─ AppRouter │ ├─ GuestRouter │ └─ rootRouter.js ├─ Assets │ ├─ fonts │ ├─ icons │ └─ images ├─ Constants ├─ Modules │ ├─ Common │ ├─ Components │ ├─ Screens │ └─ Views ├─ ReduxSrore │ ├─ sagas │ ├─ slices │ └─ store.js ├─ Static │ └─ Images └─ Utils ├─ functions.js ├─ helpers.js └─ utils.js ← environment config lives here
02

Switch the environment

Flip the active case from devFR to prodFR and bump the version

getKeyValueUrl() in utils.js switches on an environment string to decide which API URL, keys, and app version get baked into the build. Before cutting a release, that switch needs to change from devFR to prodFR, and the version inside the prodFR case needs to be bumped.

− switch ('devFR') {
+ switch ('prodFR') {
const getKeyValueUrl = () => {
  let key, url, value, version, heroku, gSignInWCID;

  // change 'devFR' to 'prodFR' to build for production
  switch ('prodFR') {

    case 'prodFR':
      url     = 'https://www.foodrelated.com/';
      value   = "kPiiX8kNoPEFLCauSAXuaol0UJsxNW/h0S3ZFYMRYm0=";
      key     = "fcca0c3c73eb935ea9e5b80571d16a73";
      // bump the version — e.g. 1.4.5 → 1.4.6
      version = '1.4.6';
      heroku  = 'https://curbsy.herokuapp.com/reserve/FoodRelatedCurbside/1669183200/13/';
      gSignInWCID = '265662000436-jgc9nqbp7v565l6qt2c8gdfk6l7b4qsv.apps.googleusercontent.com';
      break;
  }

  return { key, url, value, version, heroku, gSignInWCID };
};
  • Switch statement input changed from 'devFR' to 'prodFR'
  • Inside the prodFR case, version incremented (e.g. 1.4.5 → 1.4.6)
  • File saved
03

Swap the GoogleService-Info file

Point the iOS project at the production Firebase config

The iOS project keeps three GoogleService-Info plists side by side: the active one Xcode actually reads, plus a dev and a prod copy kept in the repo for reference.

ios ├─ AppDelegate.mm ├─ GoogleService-Info.plist ← active file Xcode reads ├─ GoogleServiceDevFR-Info.plist dev copy ├─ GoogleServiceProd-Info.plist prod copy ├─ Podfile ├─ Podfile.lock ├─ foodrelatedDevFR-Info.plist ├─ foodrelatedDevFR.entitlements ├─ foodrelatedProd-Info.plist └─ foodrelatedProd.entitlements

Replace GoogleService-Info.plist with a copy of GoogleServiceProd-Info.plist before releasing, so the build ships pointed at production Firebase.

04

Bump the Android version

Update versionCode / versionName in build.gradle

Open the android folder inside app and find build.gradle. The production flavor under productFlavors is what ships to the Play Store — increment its version there.

productFlavors {
  staging {
    applicationId "com.foodrelated.devFR"
    versionCode 1
    versionName "1.0"
    applicationIdSuffix ".stage"
  }
  production {
    applicationId "com.foodrelated.release"
    // increment both together
    versionCode 1066
    versionName "1.0.66"
    applicationIdSuffix ".prod"
  }
}
− versionCode 1065 · versionName "1.0.65"
+ versionCode 1066 · versionName "1.0.66"
⚠
Always increment, never reuse. If a build gets rejected in the Play Console, the next upload still needs a new, higher versionCode — the Play Store will not accept a repeat.
05

Point at the release keystore

gradle.properties

In gradle.properties, comment out the debug signing lines and uncomment the release keystore lines so the production build is signed correctly.

  • Comment out line 44 and line 45 (debug keystore)
  • Uncomment line 47 and line 48 (release keystore)
06

Xcode: build, archive, distribute

Ship the iOS build to TestFlight / App Store Connect

  1. Open the project in Xcode — select the .xcworkspace file, not .xcodeproj.
  2. Select the FoodrelatedProd scheme, and set the run destination to Any iOS Device (arm64).
  3. Enter the new version in the target's Identity panel and press Enter.
  4. Product → Clean Build Folder.
  5. Product → Build, and wait for it to complete.
  6. Product → Archive, and wait for it to complete.
  7. From the Organizer, click Distribute App to send the build to the App Store.
  8. Click Validate — once validation passes, the build appears under the TestFlight section in App Store Connect.
  9. In the Distribution section, use the + icon to attach the build to a new release version.

07

Android: build & publish

Generate the .aab and roll it out in the Play Console

  1. In Android Studio, select the Food Related run configuration — com.foodrelated.release.prod.
  2. In the code editor's terminal, run the production build command:
yarn android-prod-release

Once the build finishes, open the output folder and grab the generated .aab bundle.

  1. In the Play Console, go to Test and release → Production and click New release.
  2. Upload the .aab bundle.
  3. Add the release notes and click Next.
